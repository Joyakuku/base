# Markdown 撰写格式指南

本指南用于统一 `knowledge_base` 中知识文档的结构和写法。

目标是让每篇文档都能长期维护：
先说明是什么和什么时候用，
再给出可执行流程、最小示例、注意点和后续复习点。

---

## 适用场景

新增或重构以下文档时，
优先参考本格式：

- ESP32 外设配置指南。
- 芯片手册阅读笔记。
- 工具使用指南。
- 可复用工作流说明。
- 从草稿整理成知识文档。

如果只是临时记录一次问题排查，
可以先写短笔记；
等内容稳定后再整理成本文档格式。

---

## 标准结构

推荐顺序如下：

1. `# 标题`
   写清主题和用途。

2. 开场说明
   用两到五行说明“是什么”和“解决什么问题”。

3. `## 初始化流程` 或 `## 工作流程`
   用编号列表给出整体顺序。

4. `## 常用概念`
   解释后文会反复出现的核心术语。

5. `## 1. 第一步`
   按流程拆分操作步骤。

6. `## 完整示例` 或 `## 最小模板`
   给出可直接复用的代码或模板。

7. `## 常见注意点`
   收敛高频坑点。

8. `## 速查`
   列出关键函数、命令、字段或章节。

9. `## 后续扩展复习点`
   保留生疏、疑问和未来要深入的主题。

---

## 开场写法

开场只回答两个问题：

- 这是什么。
- 它主要解决什么问题。

示例：

```md
SPI 是 Serial Peripheral Interface，
常用于 ESP32 和显示屏、传感器、Flash、SD 卡等外设之间的高速同步通信。

ESP-IDF 中常见两类 SPI 使用方式：

- 普通 SPI master 设备
  先初始化 SPI 总线，
  再把一个或多个从设备挂到总线上。

- SD 卡 SPI 模式
  通过 SD SPI + FatFS 挂载，
  挂载后使用文件接口访问 SD 卡。
```

注意：

- 不要用“简介”当正文。
- 不要一开始写太长背景。
- 优先让读者快速判断这篇文档是否相关。

---

## 流程写法

流程用于建立全局地图。

硬件配置类文档使用：

```md
## 初始化流程
```

工具和方法类文档使用：

```md
## 工作流程
```

流程建议使用编号列表：

```md
典型初始化顺序如下：

1. 选择外设实例和 GPIO。
2. 配置总线或控制器。
3. 添加设备或通道。
4. 执行读写或启动输出。
5. 不再使用时释放资源。
```

注意：

- 流程只写顺序，不展开细节。
- 每一步后文最好能找到对应章节。
- 图片可以放在流程标题下方。

## 概念写法

`常用概念` 用于解释后文反复出现的名词。

推荐格式：

```md
## 常用概念

### Handle

`xxx_handle_t` 表示一个驱动实例。

创建、配置、启动、停止等操作，
都需要通过这个句柄指定目标对象。
```

适合放入概念区的内容：

- handle。
- bus / device / channel。
- timer / resolution / duty。
- mode / address / transaction。
- callback / dispatch method。

不适合放入概念区的内容：

- 大段历史背景。
- 已经能在步骤中说明的细节。
- 后续不再出现的冷门术语。

---

## 步骤写法

步骤标题使用二级标题，
并保持编号：

```md
## 1. 配置 SPI 总线
## 2. 添加 SPI 从设备
## 3. 执行 SPI 数据交换
```

每个步骤建议包含：

1. 最小代码片段。
2. 配置项说明。
3. 必要注意点。

配置项说明推荐这样写：

```md
配置项说明：

- `clock_speed_hz`
  设置 SPI 时钟频率，
  单位为 Hz。
  该值应参考从设备数据手册。

- `mode`
  设置 SPI 模式，
  由 CPOL 和 CPHA 决定。
```

注意：

- 一个配置项一条 bullet。
- 参数名用反引号。
- 先写作用，再写单位、边界和推荐值。
- 不要把代码注释当作文档主体。

---

## 示例写法

示例应能直接复制后改引脚或参数。

推荐包含：

- 必要 `#include`。
- 必要 `#define`。
- 初始化函数。
- 最小读写或启动函数。

示例后用短列表解释它表示什么：

```md
以上示例表示：

- 使用 `SPI2_HOST`。
- `MOSI = GPIO23`。
- SPI 时钟为 `10 MHz`。
- SPI mode 为 `0`。
```

注意：

- 示例不追求覆盖所有高级功能。
- 示例应避免无关业务逻辑。
- 长示例比短示例更容易过期，
  只保留最小可用路径。

---

## 注意点写法

`常见注意点` 用于收敛高频错误。

推荐每个坑点用三级标题：

````md
## 常见注意点

### length 单位是 bit

`spi_transaction_t.length` 的单位是 bit。

常见写法：

```c
trans.length = len * 8;
```
````

注意：

- 每篇控制在三到八个注意点。
- 优先写会导致功能失败、数据错误或硬件风险的问题。
- 能给出正确写法时，不只写“不要这样”。

---

## 速查写法

`速查` 用于快速回忆入口。

适合列出：

- 常用函数。
- 常用命令。
- 常用字段。
- 手册关键词。
- 文件路径。

格式：

```md
## 速查

1. `spi_bus_initialize`
   初始化 SPI 总线。

2. `spi_bus_add_device`
   向 SPI 总线添加从设备。
```

注意：

- 速查只写一句作用。
- 不在速查里展开大段解释。
- 顺序最好和正文流程一致。

---

## 后续扩展复习点写法

`后续扩展复习点` 用于保留还没完全掌握的内容。

它不是垃圾桶，
而是未来维护的路线图。

推荐写法：

```md
## 后续扩展复习点

1. DMA 缓冲区要求
   复习 DMA-capable memory、
   4 字节对齐、
   `spi_bus_dma_memory_alloc` 的适用场景。

2. SPI 时钟和采样时序
   继续学习 `clock_source`、`clock_speed_hz`、
   `input_delay_ns` 和 GPIO matrix 延迟。
```

适合放入这里的内容：

- 原草稿中的疑问。
- 暂时只知道名字的参数。
- 需要查手册或官方文档的高级主题。
- 未来可以独立成文的内容。

不适合放入这里的内容：

- 已经在正文解释清楚的内容。
- 和主题无关的想法。
- 没有复习价值的临时 TODO。

## 语言风格

本知识库默认使用短句。

推荐：

- 一句话只表达一个重点。
- 多用编号流程和参数说明。
- 中文解释为主，保留英文术语。
- 函数、字段、路径、命令使用反引号。
- 中英文术语首次出现时可以并列说明。

避免：

- 聊天式长段落。
- 没有结论的背景铺垫。
- 只写“看手册”但不说看哪里。
- 把草稿问题留在正文里。
- 同一个概念在不同文档中使用不同叫法。

## Markdown 细节

### 标题

- 每篇只使用一个一级标题。
- 主结构使用二级标题。
- 子概念和坑点使用三级标题。
- 不要跳级使用标题。

### 列表

- 流程用编号列表。
- 参数说明用无序列表。
- 速查用编号列表。
- 同类条目保持同一种格式。

### 代码块

代码块应带语言标识：

````md
```c
// code
```
````

常用标识：

- `c`
- `md`
- `text`
- `json`

### 表格

表格适合对比参数、模式、关键词。

表格不要过宽。
如果一行解释太长，
改成 bullet 更好维护。

### 分隔线

一级结构之间可以使用：

```md
---
```

不要在每个小段落之间都加分隔线。

1. 第一步。
2. 第二步。
3. 第三步。

  说明字段作用。

// 最小可用示例
```

````

## 发布前检查

提交前至少检查：

- 开场能否在一分钟内说明主题。
- 是否有整体流程。
- 是否解释了核心概念。
- 示例是否能作为最小可用路径。
- 注意点是否覆盖高频坑。
- 速查是否能快速回忆入口。
- 生疏和疑问是否收进后续复习点。
- 代码围栏是否成对。
- 标题层级是否清晰。
